# یکپارچه‌سازی‌های خارجی — وضعیت و مراحل باقی‌مانده

این سند دقیقاً مشخص می‌کند چه چیزی **کار می‌کند**، چه چیزی **آماده ولی نیازمند پیکربندی** است و مراحل اتصال هر یک.

## ۱) درگاه پرداخت

**وضعیت: لایه انتزاعی کامل + درگاه TEST برچسب‌دار.**

- مدل Payment مستقل از Order است (provider, authority, refId, status).
- جریان فعلی: `POST /api/orders` → سفارش `UNPAID` → کاربر در صفحه سفارش درگاه «پرداخت آزمایشی» را می‌بیند (برچسب: «حالت تست — هیچ پول واقعی جابه‌جا نمی‌شود») → `POST /api/orders/[id]/pay-test` → Payment(PENDING) → شبیه‌سازی callback → Payment(PAID, refId=TESTPAY-xxxx) → Order = CONFIRMED.
- **هیچ سفارشی بدون این مرحله «پرداخت‌شده» نمی‌شود**؛ مبالغ همیشه از رکورد سرور خوانده می‌شود.

**مراحل اتصال درگاه واقعی (Zarinpal/Zibal/Saman):**
1. `PAYMENT_MERCHANT_ID` را در `.env` تنظیم کنید.
2. در `src/lib/server/` یک `payment-provider.ts` بسازید با همین قرارداد: `createPayment(order) → {redirectUrl, authority}` و `verifyCallback(authority) → {ok, refId}`.
3. اندپوینت callback عمومی (مثلاً `/api/payments/[provider]/callback`) اضافه کنید که verify را صدا بزند و همان کدی را که pay-test برای PAID/CONFIRMED اجرا می‌کند، فراخوانی کند.
4. `paymentProvider` سفارش را روی نام درگاه قرار دهید. هیچ منطق سمت کلاینت تغییر نمی‌کند.

## ۲) فید ترب (Torob)

**وضعیت: آداپتور ماژولار پیاده‌سازی و تست شده؛ تطبیق نهایی فیلدها نیازمند مستندات رسمی ترب است.**

- اندپوینت‌ها:
  - `GET /api/torob/feed` → JSON (`TorobFeedResponse`)
  - `GET /api/torob/feed?format=csv` → CSV با BOM UTF-8
  - `GET /api/torob/validate` → گزارش اعتبارسنجی (فیلدهای خالی/هشدارها)
- فیلدها: product_id, product_name, brand, category, price_toman (قیمت لحظه‌ای DB), availability, page_url (canonical از `NEXT_PUBLIC_SITE_URL`), image_url, sku, warranty_months.
- منطق در `src/lib/server/torob.ts` — نگاشت فیلدها در یک ماژول جدا تا با مشخصات نهایی فقط همان فایل تغییر کند.
- **مراحل باقی‌مانده:** فیلدهای الزامی/اختیاری و مکانیزم تحویل فید (URL عمومی، آپلود دستی در پنل ترب، یا API) باید با مستندات رسمی ترب تطبیق داده شود. هیچ اندپوینت/احراز هویت فرضی از سمت ما ساخته نشده است.

## ۳) نرخ ارز (پricing engine)

**وضعیت: موتور کامل + ورود دستی نرخ (ADMIN) فعال؛ تأمین‌کننده خودکار پندینگ.**

- جریان فعلی: مدیر در `#/admin/pricing` نرخ ارز (USD/EUR/AED) را دستی ثبت می‌کند (source=MANUAL) → موتور در پیش‌نمایش، محصولات ارزی (isPriceManual=false) را محاسبه می‌کند → پس از تأیید صریح، قیمت‌ها اعمال و در PriceHistory + AuditLog ثبت می‌شوند.
- محافظ‌ها: نرخ قدیمی‌تر از ۷ روز → skip با برچسب «نرخ ارز قدیمی»؛ نرخ ثبت‌نشده → skip؛ قیمت دستی → همیشه skip. هیچ تغییری بی‌صدا رخ نمی‌دهد.
- **مراحل اتصال تأمین‌کننده (مثلاً یک API معتبر نرخ):**
  1. `FX_PROVIDER_URL/API_KEY` را تنظیم کنید.
  2. یک fetcher در `src/lib/server/` بنویسید که نرخ را گرفته و با source=نام‌سرویس در ExchangeRate ثبت کند (همان قرارداد POST /api/admin/pricing/rates).
  3. یک Cron/صف اجرا دوره‌ای — ثبت نرخ همچنان به‌صورت دستی قابل override است (رکورد فعال جدیدتر برنده است).

## ۴) حساب‌های کاربری و بازیابی رمز

- ثبت‌نام/ورود با موبایل + رمز فعال است. بازیابی رمز نیازمند سرویس پیامک/ایمیل است — فعلاً «تماس با پشتیبانی» توصیه می‌شود (در UI برچسب شفاف دارد). پس از تهیه سرویس پیامک، کد یک‌بارمصرف به User اضافه و اندپوینت reset ساخته می‌شود.

## ۵) آپلود تصویر محصول

- در این محیط storage پایدار وجود ندارد؛ پنل مدیریت تصویر را با **URL** می‌پذیرد (پیش‌نمایش زنده + fallback خودکار به placeholder).
- برای تولید: یک Object Storage (S3/ArvanCloud) و اندپوینت آپلود با اعتبارسنجی نوع/حجم فایل اضافه کنید؛ جدول ProductImage آماده است.
